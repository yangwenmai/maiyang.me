## 起因

CastMind 最近把「网络」页重做成了一张 AI 人才版图：193 位 AI 领袖、414 家机构、803 段任职，一盏灯一个点，谁在哪里工作过就连一条线。

做完之后我自己点了一下，给 Agent 留了这么一句：

> 我点击网络 tab ，初始化会先卡住，这里体验上可以做优化，就是先出现 loading 页面会好过没有任何响应。

loading 加上之后，我又点了一下，又留了一句：

> 现在的 网络 加载渲染 算法或者性能上严重卡顿，需要重新优化。

这两句话其实对应了两个完全不同的瓶颈。第一个在「加载」，第二个在「渲染」。

这篇按真实发生的顺序写，包括走偏的地方。

## 先说结论

直接上一批数据（生产构建，1440×900，Retina 2 倍像素，无头 Chromium）：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 点击到出现 loading | 没有 loading，页面没反应 | 0.2–0.5 秒 |
| 点击到地图出现 | 5–11 秒（这是加了 loading、缓存还坏着的版本） | 约 0.6 秒 |
| 服务端渲染这一页 | 1.7–2.2 秒，每次都一样 | 0.14–0.4 秒（进程启动后第一次约 1 秒） |
| 时间回放 | 55fps，偶尔一帧 117ms | 60fps |
| 回放结束后静止 | 34fps | 60fps |
| 拖动 | 33fps | 60fps |
| 放大后静止 | 16fps | 60fps |
| 放大后悬停 | 17fps | 55fps |

最原始的版本（没有 loading、布局在两端各算一次）我没有在生产模式下单独测「点击到出图」，这一格 [数据待确认]。

## 第一个坑：loading 只是止痛药

用户说「先出 loading」，最省事的做法就是加一个 `loading.tsx`。

Agent 没有直接加，而是先量了一下页面到底在等什么。

结果很意外：数据本身只要 **4ms**，真正慢的是布局。

这张图用的是 d3-force 力导向布局，每次渲染都要现场跑 420 步模拟。单独拿出来测：

```
buildModel 5189 ms
buildModel 4482 ms
buildModel 3748 ms
graph 4 ms payload 247 KB
```

更糟的是它跑了两遍：

1. 服务端渲染时跑一遍，所以点击之后几秒没反应；
2. 浏览器水合（hydration）时再跑一遍，主线程又被占住几秒。

只加 loading，只能盖住第 1 段。第 2 段一样卡，而且 loading 动画本身也会被冻住。

> **用户说要什么，是症状；量出来慢在哪，才是病。**

## 布局为什么要在浏览器里算❓

想清楚这个问题，解法就出来了。

这个布局有两个特点：结果是确定的（固定随机种子，有测试保证），而且只取决于数据。数据不变，布局就不变。

那就没必要每次渲染都算，更没必要在用户的浏览器里算。

改法分三步：

1. 服务端算一次，把约 600 个节点的坐标缓存在内存里，缓存键是数据内容的 sha1；
2. 浏览器直接拿坐标组装模型，跳过模拟，带坐标时组装只要 10ms 左右；
3. 再加一个和地图同色的 `loading.tsx`，让点击后立刻有反馈。

## 我自己埋的雷：一个没人读的时间戳

改完之后，开发模式下 loading 要 5 到 17 秒才出来。

这个数字不能用：开发服务器每次导航都在现场编译。

换成生产构建再测，loading 0.3 秒就出来了，但地图还是要 5 到 11 秒。

用 curl 直接打服务端：

```
network ttfb=1.87s
network ttfb=2.22s
network ttfb=1.72s
leaders total=0.05s
```

同一个服务，领袖页 50ms，网络页 2 秒，而且「热」了也不变快。

那只有一种可能：**缓存根本没命中**。

把同一份数据连续取两次，算哈希，结果 `same key false`。

罪魁是图谱数据里的一个字段：

```ts
return { people, orgs, affiliations, generatedAt: new Date().toISOString() };
```

每次组装都写进当前时间，哈希当然每次都变。

全仓库搜了一下，这个字段只有赋值，没有任何地方读它。删掉之后，服务端从 1.7–2.2 秒降到 0.14–0.4 秒。

说实话，这个坑是这次重构时我们自己写进去的，不是历史遗留。顺手补了一个测试：同样的输入组装出的图谱必须逐字节相同，防止以后谁再往里塞时间戳。

> **加了缓存，一定要测一次命中率。没测过的缓存，等于没有缓存。**

## 第二个坑：我以为是 JS 慢，其实是像素

加载的问题解决了，第二句反馈说的是「渲染严重卡顿」。

Agent 读完画布代码，列了一串嫌疑：

- 每帧都整张重画，静止时也在画；
- 每帧逐条描 803 条线、画约 600 个光晕；
- 每帧都在测量文字宽度，标签碰撞检测是两两比较；
- 回放时每一帧都触发 React 整棵树重渲染。

看起来哪条都像。但它没有直接改，先分场景测帧率，同时开 CPU 采样。

结果把这份嫌疑名单推翻了一大半：

```
== idle: fps=34 p50=33ms p95=50ms
    96.0% (program)
    1.6% S page-xxx.js
    1.2% drawImage
== zoomed-idle: fps=16 p50=67ms p95=84ms
    98.1% (program)
    0.8% S page-xxx.js
    0.6% drawImage
```

JS 函数加起来不到 3%。86% 到 98% 的时间记在 `(program)` 名下，也就是浏览器自己的光栅化和合成。

瓶颈是**像素填充**（fill rate）：

- 每个点都有一个光晕贴图，用叠加混合（`lighter`）画上去，混合要逐像素算；
- 光晕按世界坐标缩放，放得越大，屏幕上的光晕就越大，放大后只剩 16fps；
- Retina 屏上像素数再乘 4；
- 节点有一个「呼吸闪烁」效果，逼着静止时也每帧整张重画，所以静止只有 34fps。

名单里的「measureText」「React 重渲染」，在采样里几乎看不见。

## 第二个坑是怎么改的？

按收益从大到小，三处：

**1. 按需重绘。** 静态画面先画到一张离屏画布，只有视角、年份、选中、悬停变了才重画。每一帧只是把这张图贴上去。Pro 版的人才流动粒子单独画在上面一层，不触发整张重画。

**2. 光晕设屏幕像素上限。** 机构最大 56px，人物最大 16px，放大不再跟着变大：

```ts
const glow = Math.min(
  lone ? n.r * 2.2 : n.type === 'org' ? n.r * 4.2 : n.r * 5,
  GLOW_MAX_PX[n.type] / t.k,
);
```

**3. 屏幕外不画。** 节点和连线先判断在不在视口里。连线要用两个端点加贝塞尔控制点的包围盒判断，只看端点的话，放大后穿过屏幕的长线会消失。Agent 第一版就是只看端点，写完自己发现不对，又改了回来。

另外把标签宽度缓存了一下，这个收益很小，算顺手。

改完重测：回放、静止、拖动、放大四个场景全部 60fps，p95 都在 18ms 以内。

![优化前放大后的画面：光晕很大，叠在一起](https://raw.githubusercontent.com/yangwenmai/maiyang.me/master/blog/ai-atlas-perf-zoomed-before.png)

![优化后放大后的画面：光晕有上限，画面更清爽](https://raw.githubusercontent.com/yangwenmai/maiyang.me/master/blog/ai-atlas-perf-zoomed-after.png)

这两张不是同一个位置、同一个缩放级别，只用来看光晕大小的差别。

## 从用户的角度看，变了什么🤔

技术指标是给工程师看的，用户感觉到的是这几件事：

- 点「网络」，0.2 到 0.5 秒内就能看到标题和闪烁的光点，知道页面在加载，不会以为点坏了；
- 0.6 秒左右地图出来，回放从 1998 年开始一年一年亮起来，不再一顿一顿；
- 拖动和缩放跟手，放大看人名时不再掉到每秒十几帧；
- 鼠标悬停有轻微掉帧（55fps），我判断大部分人感觉不到。

但也有代价，要写出来：

- **呼吸闪烁没了。** 节点改成固定亮度，这是按需重绘的前提。想要回来，只能做在粒子那一层。留不留，我还没定 [待确认]；
- **放大后的光晕变小了。** 我觉得更清爽，但这是审美判断，不是性能判断。

## 你明天能怎么用？

如果你也在做 Canvas、地图、关系图这类页面，我会按这个顺序问自己：

- 用户说「加个 loading」的时候，我量过页面到底在等什么吗？
- 这个计算结果是确定的吗？确定的话，为什么要在每个用户的浏览器里算一遍？
- 我加的缓存，测过命中率吗？缓存键里有没有时间戳、随机数这种每次都变的东西？
- 我的性能数字是在开发模式下测的吗？
- CPU 采样里，JS 占多少？如果大头是 `(program)`，我该看的是像素，不是代码；
- 画面静止的时候，画布还在每帧重画吗？
- 有没有什么东西的尺寸，会跟着缩放倍数无限变大？

前两条解决了加载，后面几条解决了渲染。

## 我不确定的地方

- 所有帧率都是在无头 Chromium 里测的，它用的是软件渲染，像素填充的开销会被放大。真实 Mac + GPU 上的数字 [数据待确认]，我的推测是优化前没这么夸张，但优化后的结论不变；
- Pro 版粒子动画没测到，无头浏览器没法登录 Pro 账号。从结构上看它每帧只叠画几十个粒子，开销应该很小，但我没有数字；
- 服务端缓存是进程内存，Serverless 冷启动后的第一次请求还是要算约 1 秒，靠 loading 盖住。要彻底解决，得在构建时预计算，这次没做。

## 写在最后

如果把这次经历压缩一下，我会留下三句话：

1. **用户说的解法，先当成症状来量。**
2. **缓存加完，测命中率。**
3. **先采样，再动手。读代码列出来的嫌疑名单，一大半是错的。**

这次的代码基本都是 Cursor 里的 Coding Agent 写的，我做的事是提出两句反馈、看前后对比的数字。它写得很快，但真正决定往哪改的，每一次都是测量结果，不是它（或者我）的直觉。
